# 데이터 모델 초안 리뷰

본 문서는 `User`, `Place`, `Visit`, `VisitPosition`, `UserPlaceFirstArrival` 다섯 개 테이블 초안에 대한 검토와 Spring Data JPA 매핑 시 주의점을 정리한 자료입니다. 실제 DDL은 `src/main/resources/schema-postgres.sql`에서 관리하며, 사전에 `postgis`/`uuid-ossp` 확장을 설치해야 합니다.

## 공통 가이드

- 모든 엔티티는 `BaseEntity`를 상속해 `created_at`, `updated_at`, `deleted_at`을 공통으로 관리합니다.
- 소프트 딜리트는 `deleted_at`을 `NULL` ↔️ 타임스탬프로 전환하는 방식으로 처리하며, 필요 시 `@SQLDelete`, `@Where`로 자동 필터링을 추가할 수 있습니다.
- 타임스탬프는 `OffsetDateTime`(TIMESTAMPTZ 매핑) 사용을 권장합니다. KST 기준 계산이 필요하면 서비스 레이어에서 보정하세요.
- JSON/배열/ENUM 등 PostgreSQL 고유 타입은 Hibernate 표준 타입(`@JdbcTypeCode`)으로 매핑하거나 전용 타입 핸들러가 필요합니다. 아래 각 항목에 권장 접근법을 정리했습니다.
- Spring Boot 3.5.x에서 제공하는 Hibernate 6.6 기능을 활용해 JSON/배열 컬럼을 `@JdbcTypeCode(SqlTypes.JSON)` / `@JdbcTypeCode(SqlTypes.ARRAY)`로 매핑합니다.

```java
@JdbcTypeCode(SqlTypes.JSON)
@Column(columnDefinition = "jsonb")
private WorkingHours workingHours;

@JdbcTypeCode(SqlTypes.ARRAY)
@Column(columnDefinition = "text[]")
private String[] category;
```

## User

| 필드 | 매핑 제안 | 비고 |
| --- | --- | --- |
| `id` (UUID) | `@Id @GeneratedValue(strategy = GenerationType.AUTO)` + `UUID` | PostgreSQL `uuid-ossp` 확장 필요 시 인프라 레벨에서 설치. JPA는 `uuid` 타입을 인식합니다. |
| `email`, `name`, `password`, `provider` | `@Column(length = … , nullable = …)` | `provider`는 `EnumType.STRING` 권장. `LOCAL`일 때 `password` 필수 조건은 서비스/도메인 레이어 검증으로 처리. |

**보완 제안**

- `provider=LOCAL`일 때 `password` NOT NULL 제약을 데이터베이스 레벨에서 강제하려면 `CHECK` 제약(예: `CHECK ((provider = 'LOCAL' AND password IS NOT NULL) OR (provider <> 'LOCAL' AND password IS NULL))`)을 추가로 정의해야 합니다. JPA 스키마 생성으로는 부족하니 수동 DDL이 필요합니다.

## Place

| 필드 | 매핑 제안 | 비고 |
| --- | --- | --- |
| `category` (`VARCHAR[]`) | `String[]` + `@JdbcTypeCode(SqlTypes.ARRAY)` + `columnDefinition = "text[]"` (getter는 `List` 변환) | Hibernate 6 표준 배열 타입 사용. 필요 시 조인 테이블로 정규화 가능. |
| `working_hours` (`JSONB`) | `@Column(columnDefinition = "jsonb")` + `@JdbcTypeCode(SqlTypes.JSON)` | |
| `break_time` (JSON 포맷 문자열) | `@Column(columnDefinition = "jsonb")` + `@JdbcTypeCode(SqlTypes.JSON)` 로 저장 권장, 아니면 `VARCHAR(20)` 그대로 사용 | JSON으로 저장하면 구조 검증이 쉬워짐. |
| `lat`/`lng` (`DECIMAL(9,6)`) | `BigDecimal` + `@Column(precision = 9, scale = 6)` | 거리 계산용 double로 변환 시 주의. |
| `location` (`GEOGRAPHY(Point,4326)`) | 별도 컬럼으로 저장, `@Column(columnDefinition = "geography(Point,4326)")` | `ST_DWithin` 등 공간 연산 최적화를 위해 Lat/Lng에서 파생 저장 권장. |
| `opened_at_source` (JSONB) | `@Column(columnDefinition = "jsonb")` + JSON 타입 매핑 | |
| 주소 필드들 | `@Column(length = …)` | `addr_sido` 20, `addr_sigungu` 30, `addr_eupmyeondong` 80, `addr_street` 100, `addr_detail` 100. |

**추가 고려:** GIN 인덱스, lower(name) 함수 인덱스, 공간 인덱스(`GIST(location)`)는 DDL 스크립트로 별도 관리가 필요합니다. Flyway를 쓰지 않는 경우 `src/main/resources/schema-postgres.sql`과 같은 초기 스크립트를 운영하세요.

## Visit

| 필드 | 매핑 제안 | 비고 |
| --- | --- | --- |
| `visit_id` | `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)` + `Long` | |
| `user_id`, `place_id` | `@ManyToOne(fetch = LAZY)` | FK 유지. |
| `state`, `client_mode` (ENUM) | `EnumType.STRING` | `visit_state`, `client_mode` enum 정의 필요. |
| `dwell_started_at` (`TIMESTAMPTZ`) | UC-GEO-1/4를 위해 추가 저장 권장 | 서버 재기동 후에도 180초 누적 상태를 이어가기 위함. |
| `last_accuracy_m` (`NUMERIC(6,2)`) | `BigDecimal` | |
| `meta` (`JSONB`) | JSON 타입 매핑 필요. |

**Soft delete:** 세션 데이터는 보존 정책에 따라 `deleted_at` 사용 여부 결정. 만약 실제 삭제를 적용한다면 `@SQLDelete`로 소프트 딜리트 동작 커스터마이징 필요. UC-GEO-5 상태 머신 일관성을 위해 `state` 전환은 트랜잭션 내에서만 수행하세요.

## VisitPosition

| 필드 | 매핑 제안 | 비고 |
| --- | --- | --- |
| `pos_id` | `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)` | |
| `visit_id` | `@ManyToOne(fetch = LAZY)` | `@Index(name = "idx_visit_position_visit_received", columnList = "visit_id, received_at")` 추가 권장 (스프링 JPA `@Table(indexes=...)` 가능). |
| `lat`/`lng`, `accuracy_m`, `mode`, `received_at` | 위와 동일 | |

**보존 전략:** 파티셔닝/TTL이 필요하다면 PostgreSQL 파티션 테이블이나 `DROP PARTITION` 스케줄링을 고려. 이는 JPA로 자동 생성 불가 → 수동 SQL 스크립트(예: cron + `ALTER TABLE detach partition`)로 관리.

## UserPlaceFirstArrival

| 필드 | 매핑 제안 | 비고 |
| --- | --- | --- |
| 복합 PK (`user_id`, `place_id`) | `@EmbeddedId` + `@MapsId` 패턴 | JPA 표준 방법. |

**데이터 채움:** 애플리케이션에서 최초 도착 시 저장하거나, 배치/트리거 활용. JPA로는 트리거 생성이 불가하므로 수동 SQL/배치 작업 필요.

## Use Case 커버리지 점검

| UC | 요구 데이터 | 현재 필드 상태 | 보완 제안 |
| --- | --- | --- | --- |
| UC-GEO-1 (지오펜스 판정) | 방문 세션 상태, 위치 이벤트, 반경 계산, dwell(180s) | `Visit`에 상태/시간, `VisitPosition`에 좌표/정확도 있음 | `Visit`에 `dwell_started_at` 추가, `Place`에 `location`(geography) 컬럼 및 `GIST` 인덱스 필요 |
| UC-GEO-2 (도착 정정) | 수동 확정/취소, 세션 상태 기록 | `Visit.state`, `arrived_at`, `cancelled_at` 존재 | 정정 플래그 로그용 컬럼(예: `manual_override_by`) 고려, UI 메타는 별도 로깅 |
| UC-GEO-3 (목적지 변경) | 세션 취소/신규 시작, 상태 전이 트랜잭션 | `Visit.cancelled_at`, `state` | 동일 유저가 다중 ACTIVE 갖지 않도록 유니크 인덱스(`unique(user_id) where state in ('ACTIVE')`) 권장 |
| UC-GEO-4 (근처 통과) | dwell 리셋 상태 유지 | `Visit`에 타이머 정보 없음 | `dwell_started_at` 또는 `dwell_accumulated_seconds` 컬럼 추가 |
| UC-GEO-5 (세션 종료) | 타임아웃/취소/정상 종료 기록 | `started_at`, `expired_at`, `cancelled_at`, `arrived_at` 존재 | 타임아웃 배치용 조회 인덱스(`state='ACTIVE'` + `started_at`) 추가 |
| UC-GEO-6 (검색/룰렛) | 반경, 미방문, 신규 여부, 카테고리 | `Place` + `UserPlaceFirstArrival` + 주소 정보 | `Place`에 `location`과 공간 인덱스 필수, `opened_at` + `first_seen_at`(없음) → 신규 판정 위해 `first_seen_at` 컬럼 추가 권장 |
| UC-GEO-7 (빈 결과 완화) | 검색 메타 저장 | 응답 메타로 처리 가능 | 완화 전략 로깅용 `search_relax_logs` 별도 테이블 고려 |

## 타입/제약 유의 사항 요약

- **UUID ↔ BIGINT 불일치:** 현재 `User.id`는 UUID, `Visit.user_id`는 BIGINT로 정의되어 있습니다. 타입을 통일하거나, 사용자 PK를 BIGINT로 변경하는 것이 FK 일관성 측면에서 안전합니다.
- **지리정보 최적화:** Lat/Lng 분리 저장만으로는 `ST_DWithin`이 고성능으로 동작하지 않습니다. `Place`에 `geography(Point,4326)` + `GIST` 인덱스를 추가하세요.
- **Dwell 상태 보존:** UC-GEO-1/4 요구사항을 위해 `Visit`에 최소 `dwell_started_at`이 있어야 서버 재시작 후에도 연속체류 판단이 이어집니다.
- **ENUM 관리:** `visit_state`, `client_mode` enum은 DB와 코드에서 동일 문자열을 쓰도록 중앙 정의(`enum` 패키지) 필요.
- **CHECK 제약:** `User` provider/password 조건, `Visit` 상태 전이 규칙 등은 DB 레벨 제약으로 보강하면 데이터 오염을 방지할 수 있습니다.

## Spring Data JPA가 직접 생성/매핑하기 어려운 컬럼

| 항목 | 이유 | 대안 |
| --- | --- | --- |
| PostgreSQL 배열 (`category`) | Hibernate 표준 타입만으로는 List 매핑 어려움 | `@JdbcTypeCode(SqlTypes.ARRAY)` + `String[]` 사용 또는 조인 테이블로 정규화 |
| JSONB 컬럼 (`working_hours`, `opened_at_source`, `meta` 등) | JSON 직렬화 필요 | `@JdbcTypeCode(SqlTypes.JSON)` + `JsonNode` 사용 |
| 함수/GIN 인덱스 | DDL 자동 생성 불가 | Flyway/Liquibase 스크립트로 관리 |
| 테이블 파티셔닝 | JPA DDL 자동화 불가 | 수동 DDL, 뷰 + `@Subselect` 등으로 대응 |

## 추천 최적화 & 개발 흐름

1. **의존성 간소화**: Hibernate 6 표준 타입을 활용하므로 추가 라이브러리 없이 JSON/배열 매핑을 처리합니다.
2. **마이그레이션 도구 사용**: 인덱스/파티션/트리거 등은 Flyway 기반 SQL 스크립트로 관리합니다. `src/main/resources/db/migration` 디렉터리 신설 추천.
3. **Enum 전략 통일**: 모든 ENUM 필드는 `EnumType.STRING`으로 저장해 향후 enum 순서 변경 위험을 제거합니다.
4. **DTO ↔ JSON 직렬화 레이어**: `working_hours`처럼 구조가 복잡한 JSON은 값 객체(예: `WorkingHours`)를 정의하고 Jackson으로 직렬화/역직렬화하면 도메인 로직에서 안전성을 확보할 수 있습니다.
5. **Soft Delete 정책**: `deleted_at` 기반 필터링이 일관되게 적용되도록 Repository 레벨에서 `@Query("select ... where deleted_at is null")` 또는 `@Where(clause = "deleted_at IS NULL")` 사용을 검토하세요.
