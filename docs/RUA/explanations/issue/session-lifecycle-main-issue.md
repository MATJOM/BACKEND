# 메인 이슈: feat(session-lifecycle) 방문 세션 상태 전환 및 도착 판정 전체 구현 (#24)

## 배경/문제 정의
- 점심 추천 MVP는 추천 이후 실제 방문 여부를 추적할 수단이 없다.
- 세션 생성 이후 위치 이벤트 처리, 도착 판정, 타임아웃 등 핵심 흐름이 미구현 상태라 운영 데이터와 사용자 경험 모두 단절되어 있다.
- 4.x 태스크는 세션 라이프사이클 전체를 표준화해 멱등/레이트리밋/관측성 정책과 연결하려는 목적을 가진다.

## 사용자 스토리
As 서비스 운영자,
I want 사용자의 방문 세션이 시작부터 도착/만료까지 일관된 상태 전환을 따르도록 하고 싶다
so that 추천 품질을 검증하고 이상 상황을 빠르게 대응할 수 있다.

## 범위 (In/Out)
**In**
- `/api/v1/sessions` 관련 API, 서비스, 리포지토리, 스케줄러 정비
- GeoFenceEvaluator, dwell 계산, 정확도 가드, 이벤트 로깅, 테스트 시나리오
- Redis를 활용한 멱등/타임아웃/캐시 정책

**Out**
- 프런트엔드 UI 변경
- 방문 리워드/배지와 같은 후속 비즈니스 로직
- 권한/인증(8.x), 관측성(9.x) 세부 구현

## 수용 기준 (AC)
- [ ] 세션 시작~종료 전체 흐름에 대한 E2E 테스트(4.8)가 통과한다.
- [ ] 멱등키, 레이트리밋, 상태 전이가 문서화되고 OpenAPI 스펙에 반영된다.
- [ ] 도착/만료/취소 이벤트가 로그 혹은 이벤트 스토어에 누락 없이 기록된다.
- [ ] 타임아웃이 발생할 경우 재시도 없이 자동으로 EXPIRED 상태가 된다.

## API/계약 영향
- `/api/v1/sessions` 계열 엔드포인트 명세 확정 및 OpenAPI 업데이트
- 에러 코드 추가: SESSION_ALREADY_ACTIVE, SESSION_NOT_FOUND, ARRIVAL_CONFLICT 등
- 요청/응답 DTO 정리 및 테스트와 동기화

## 비기능 요구사항 (NFR)
- 위치 이벤트 처리 p95 ≤ 500ms (Redis/DB 포함)
- GeoFence 계산 정확도 ±2m 이내, accuracy>30m 이벤트는 dwell 계산에서 제외
- 타임아웃 스케줄러는 장애 발생 시 재기동 후에도 중복 없이 실행

## 의존성/리스크
- Redis 의존성: dwell/타임아웃 키 TTL 전략 미정 → 4.3/4.6에서 확정 필요
- 세션 상태 전환 예외 코드 합의 필요 → 프런트/QA와 조율 예정
- PostGIS 거리 계산과 애플리케이션에서의 Haversine 결과 일관성 검증 필요
